# Compassio 代码架构与质量分析

> 分析日期: 2026-10-17 | 分析对象: /root/compassio @ main

---

## 一、架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  Vue 3 + TS + Element Plus + Pinia (SPA, ~4800 行)          │
│  ├─ 学生端: 测评作答 / 报告查看                               │
│  ├─ 教师端: 教师自评 / 本班学生结果                           │
│  └─ 管理员端: 名单导入 / 账号管理 / 通知 / LLM 配置 / 量表管理 │
└──────────────────────────┬──────────────────────────────────┘
                           │ REST (JSON, JWT Bearer)
┌──────────────────────────▼──────────────────────────────────┐
│  FastAPI + Uvicorn (async, ~5500 行)                        │
│  ├─ routers/     9 个路由模块 (auth/assess/admin/...)       │
│  ├─ engine/      自适应选题 / 计分 / 风险规则 / 结论生成       │
│  ├─ llm/         OpenAI 兼容抽象 (provider/presets/service)  │
│  ├─ observability/  Prometheus 指标 + OTLP Trace + 结构化日志  │
│  ├─ next_cache.py  Redis 预取缓存 (next-item prefetch)       │
│  └─ security.py   JWT + bcrypt + RBAC                        │
└──────────┬──────────────┬──────────────┬────────────────────┘
           │              │              │
    ┌──────▼──────┐ ┌─────▼─────┐ ┌─────▼─────────┐
    │ PostgreSQL  │ │   Redis   │ │ LLM Gateway   │
    │ (CNPG 托管) │ │ (会话/缓存)│ │ (OpenAI 兼容) │
    └─────────────┘ └───────────┘ └───────────────┘
```

**部署形态**: 同一仓库双部署 — `docker-compose` (传统) / `kustomize + ArgoCD` (GitOps 全自动)

**代码规模**: 后端 ~5500 行 Python / 前端 ~4800 行 TS+Vue / 测试 ~2400 行 / CI-CD ~300 行 YAML

## 二、优点

### 1. 架构设计成熟 (8/10)

| 维度 | 评价 |
|------|------|
| **前后端分离** | 清晰的 SPA + API 边界，前端 axios 拦截器统一处理 token 与 401 跳转 |
| **异步全链路** | FastAPI async + SQLAlchemy 2.0 async + asyncpg + redis.asyncio，无同步阻塞调用 |
| **关注点分离** | engine (纯函数计分/选题) / routers (HTTP 层) / llm (外部抽象) / observability (横切) 分层清晰 |
| **领域建模** | User/Class/Assessment/Response/Result/ScaleDef 关系完整，断点续答与多轮测评支持到位 |
| **RBAC 权限模型** | 三角色 (admin/teacher/student) + 班级隔离 + 教师数据仅本人可见，权限边界清晰 |

### 2. 工程质量意识强 (8/10)

| 维度 | 评价 |
|------|------|
| **测试覆盖** | 13 个测试文件覆盖计分边界/风险规则/权限/流程/可观测性/导出，含端到端流程测试 |
| **可观测性** | Prometheus 指标 (route 模板化避免基数爆炸) + OTLP Trace + 结构化 JSON 日志，三件套齐全 |
| **依赖健康检查** | `/api/health` 就绪探针 + `/api/health/live` 存活探针 + 30s 后台循环，DB/Redis/LLM 三依赖独立检测 |
| **LLM 成本管控** | fusion 策略 (规则选题 + LLM 每 12-20 题检查点)，一份 100 题 MHT 仅 5-8 次 LLM 调用；`rules_only` 可完全关闭 |
| **缓存预取** | next-item 异步预取 + Redis 缓存 + 本地回退，学生端 `/next` 命中时 <20ms |
| **LLM 容错** | 超时 8s 自动回退规则；`reachable()` 免额度探活 (利用 400 不消耗 token)；推理模型截断自动放大 max_tokens 重试 |
| **跨 worker 一致性** | uvicorn 2 worker + 2 pod 探活结果通过 Redis 共享，避免重复探活 |

### 3. CI/CD 与部署 (7/10)

| 维度 | 评价 |
|------|------|
| **GitOps** | Tekton Pipeline → Harbor → gitops repo bump tag → ArgoCD 同步，全自动 |
| **安全实践** | 镜像漏洞扫描 (Harbor auto_scan)、Secret 不入 Git、GitOps 私有仓托管 |
| **双部署形态** | compose 4 命令起 / kustomize 集群部署，适配不同环境 |
| **前端容器化** | Vite 构建 + nginx 静态托管，axios baseURL `/api` 走 Ingress 路由 |

### 4. 业务逻辑严谨 (8/10)

- **计分引擎纯确定性**: LLM 绝不参与计分，严格按量表 JSON 定义
- **效度量表**: MHT 测谎 ≥7 自动作废，`is_valid` 标记 + 无效原因
- **风险预警**: 危机题命中 → 第一批时间通知管理员 (站内中心)
- **教师隐私保护**: teacher_ref 结果永不进入管理员通知，仅本人可见
- **断点续答**: 同一量表已有进行中测评直接复用，避免重复开测
- **量表热替换**: 管理员上传新 JSON 即可替换题库，无需改代码

## 三、缺点与风险

### 1. 安全性 (6/10) — 需加固

| 问题 | 严重度 | 说明 |
|------|--------|------|
| **JWT Secret 默认值** | 高 | `config.py` 默认 `"change-me-in-production"`，若环境变量未设置则使用弱密钥。生产部署必须显式覆盖 |
| **初始密码明文存储** | 中 | `User.initial_password` 字段存明文，虽注释说明"仅供打印"，但数据库泄露会暴露全部初始密码 |
| **bcrypt rounds 偏低** | 中 | 默认 10 轮 (约 50ms/hash)，OWASP 建议 ≥12。性能敏感场景可理解，但应注释说明权衡 |
| **无登录限流** | 中 | `/api/auth/login` 无 rate-limit，可被暴力破解。需依赖网关层或添加慢速 bcrypt 兜底 |
| **CORS 未显式配置** | 低 | 未看到 `CORSMiddleware`，前端走 Ingress 同源则无问题，但缺少显式白名单 |
| **API Key 存储** | 低 | LLM API Key 存 DB 明文 (LLMConfig.api_key)，未加密 |

### 2. 代码一致性 (6/10) — 可改进

| 问题 | 说明 |
|------|------|
| **通知重复检查冗余** | `_maybe_create_notification` 中先 `select` 再 `if existing is None` 再 `add`，两次相同查询，可合并为 `INSERT ... WHERE NOT EXISTS` 或依赖唯一约束 |
| **全局可变状态** | `_LAST_LLM_CHECK` / `_LLM_HEALTH` / `_route_index_cache` 等模块级全局变量，多 worker 下依赖 Redis 同步，逻辑较绕 |
| **security.py 重复 import** | `from app.config import get_settings` 和 `from app.config import get_settings as _get_settings` 重复，`_settings` 在模块加载时初始化 (潜在测试问题) |
| **前端错误处理粗糙** | `catch { // ignore }` 静默吞错，不利于排查 |
| **类型安全不完整** | 后端 Pydantic schema 完整，但 `dict[str, Any]` 大量使用 (scores/risk_flags)，丢失类型约束 |

### 3. 架构局限 (6/10) — 可扩展性天花板

| 问题 | 说明 |
|------|------|
| **单量表引擎** | 计分/选题逻辑硬编码三种量表 (mht/mssmhs/teacher_ref)，新增量表需改 `scoring.py` + `adaptive.py` |
| **无插件化量表注册** | 量表 JSON 热替换只换数据，但计分规则仍代码硬编码。理想做法是每种量表带一个 scorer 类 |
| **Redis 单点** | 未做 Redis 高可用 (哨兵/集群)，Redis 挂掉则缓存/限流/探活共享全部退化 |
| **无水平扩展设计** | 2 replica 固定，无 HPA；next_cache 本地回退在多 pod 间不共享 |
| **缺数据库迁移** | 使用 `create_all + 轻量 ALTER`，无 Alembic 迁移文件，schema 变更难以审计与回滚 |

### 4. 运维与可观测性 (7/10) — 良好但有盲区

| 问题 | 说明 |
|------|------|
| **无告警规则** | 有 Prometheus 指标但未见 Alertmanager 规则文件，需补充 (如 LLM 持续不可用、依赖 down、错误率飙升) |
| **Trace 采样策略缺失** | OTLP 未配置采样率，生产环境全量 trace 可能量大 |
| **无慢查询日志** | SQLAlchemy 未开启 `echo` 或慢查询阈值日志 |
| **前端无埋点** | 只有后端 Prometheus 指标，前端性能 (页面加载/接口延迟) 无监控 |
| **无 SLO/SLA 定义** | 缺少可用性目标与错误预算概念 |

## 四、代码风格与可维护性

### 后端 Python

- **类型标注**: 大量使用 `Mapped[...]` / `Optional[...]`，类型提示覆盖好
- **文档字符串**: 关键函数有 docstring，但部分注释偏长 (如 LLM 探活逻辑的块注释)
- **命名规范**: 整体一致，snake_case 标准，但 `_subscale_threshold` 等函数过长
- **函数长度**: `pick_next_item` (150 行) 和 `_probe_llm_reachable` 较复杂，可拆分为更小单元

### 前端 Vue 3

- **组件结构**: Composition API + `<script setup>` 规范统一
- **状态管理**: Pinia 使用轻量 (auth/notify 两 store)，符合应用规模
- **类型定义**: `types/index.ts` 集中管理，接口对齐后端 Pydantic schema
- **样式**: scoped CSS + 少量全局，无 CSS 预处理器依赖

### 测试

- **覆盖盲区**: 计分/权限/流程覆盖好，但 LLM provider 的 mock 测试、并发场景、导入边界测试不足
- **测试数据**: 依赖真实量表 JSON 文件 (scales/data/)，未 mock，集成测试风格

## 五、总结评分

| 维度 | 评分 | 一句话 |
|------|------|--------|
| 架构设计 | 8/10 | 前后端分离 + 异步全链路 + 清晰分层，小型项目中的优秀水平 |
| 代码质量 | 7/10 | 类型标注完整、命名规范，但全局状态与重复查询拉低一致性 |
| 测试覆盖 | 6/10 | 核心逻辑有测试，但 LLM mock、并发、导入边界覆盖不足 |
| 安全性 | 6/10 | JWT 默认值 + 无限流 + 明文初始密码，生产前必须加固 |
| 可观测性 | 7/10 | 三件套齐全，但缺告警规则与前端埋点 |
| CI/CD | 7/10 | GitOps 全自动， Harbor 扫描，成熟度高 |
| 文档 | 8/10 | README/SPEC/运维手册齐全，业务逻辑与技术决策记录详尽 |
| **综合** | **7/10** | **一个架构清晰、工程意识强、适合中学场景的高质量小型系统** |

### 适合场景

- 中小规模学校 (几百到几千师生) 心理健康筛查
- 单校区部署，无需多租户隔离
- 有基本运维能力的团队 (或教师自行维护)

### 不适合场景

- 大规模多校区/多租户 (需重构为多租户架构)
- 高并发场景 (无水平扩展设计)
- 严格合规要求 (教育数据需等保加固)

## 六、优先改进建议 (按 ROI 排序)

1. **[P0] 安全加固**: 生产环境强制覆盖 JWT Secret、添加登录限流 (Redis 计数器)、initial_password 加密存储或改为一次性 token
2. **[P1] 补充告警规则**: Alertmanager 配置 (LLM 持续不可用 >5min、依赖 down、5xx 错误率 >5%)
3. **[P1] 引入 Alembic 迁移**: 替代 `create_all + ALTER`，schema 变更有审计轨迹
4. **[P2] 量表引擎插件化**: 抽象 `ScaleScorer` 协议，新量表只需实现 scorer + JSON
5. **[P2] Redis 高可用**: 至少做主备 (哨兵)，避免单点故障导致全量缓存失效
6. **[P3] 前端性能埋点**: 页面加载、接口延迟、LLM 等待时长的 RUM 监控
