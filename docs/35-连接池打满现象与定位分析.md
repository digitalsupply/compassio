# 连接池打满：现象与定位分析

> 结合 Compassio 线上环境（CNPG `pg16-ceph` 集群 + 后端 SQLAlchemy 直连），分析连接池打满的现象，以及如何区分是**应用侧连接池**打满还是**数据库侧 max_connections** 打满。

## 一、线上环境基线

先看本项目的实际配置与当前数据，定位才有依据：

| 项 | 当前值 |
| --- | --- |
| PostgreSQL 集群 | CNPG `pg16-ceph`，共享集群（compassio + n8n） |
| `max_connections` | **100**（全局上限，两业务共享） |
| 连接池中间件 | **无**（无 PgBouncer、无 CNPG Pooler，应用直连 PG） |
| 后端副本数 | 1（`compassio-backend` deployment） |
| 后端引擎配置 | `backend/app/db.py:22` `create_async_engine(url, future=True)`，**未配 pool_size / max_overflow / pool_pre_ping** |
| SQLAlchemy 默认池 | `AsyncAdaptedQueuePool`，`pool_size=5`、`max_overflow=10` → **单 worker 上限 15** |
| `application_name` | **未设置**，连接来源只能靠 `client_addr`（Pod IP）区分 |
| 当前实际连接 | 约 14（compassio 4 + n8n 1 + 运维/复制若干），余量充足 |
| 长事务 | 当前 0（健康） |

**关键结论**：数据库全局上限 100，单 worker 应用侧池上限 15。两者可能各自先被打满，现象相似但根因不同，必须分开定位。

## 二、两种"打满"的本质区别

| | 应用侧连接池打满 | 数据库侧 max_connections 打满 |
| --- | --- | --- |
| 触发点 | SQLAlchemy 池内连接耗尽，**拿不到连接** | PG 收到 100 个连接后**拒绝新连接** |
| 本质 | 应用层问题（池太小 / 连接归还慢 / 泄漏） | 数据库层问题（连接总数超限） |
| PG 连接数 | 通常**远低于 100**（如 20–30） | **= 100 或接近** |
| 报错 | `sqlalchemy.exc.TimeoutError`：`QueuePool limit of size 5 overflow 10 reached, connection timed out` | `OperationalError`：`FATAL: remaining connection slots are reserved...` / `too many clients already` |

## 三、现象

### 3.1 应用侧连接池打满

- 请求处理变慢、大量请求**卡住**，最终超时返回 **HTTP 500 / 504**
- 后端日志出现 `sqlalchemy.exc.TimeoutError`（连接获取超时，默认 `pool_timeout=30s`，卡 30 秒后报错）
- 高并发下请求排队，池一满后续请求全部等待
- **数据库侧连接数并不高**，PG 可能很空闲

### 3.2 数据库侧 max_connections 打满

- 应用**无法建立新连接**，日志大量 `OperationalError: could not connect to server` / `FATAL: too many clients already`
- 新请求几乎全部失败，已建立的连接也可能受影响
- **PG 连接数 = 100**，`pg_stat_activity` 里大量 `idle` 或 `idle in transaction` 连接堆积

## 四、定位流程：判断是应用还是数据库

核心是**先看数据库连接数，再分层下钻**。

### 第一步：查数据库当前连接数（最关键）

```bash
# 定位主库
POD=$(kubectl -n cnpg-system get cluster pg16-ceph -o jsonpath='{.status.currentPrimary}')

# 总连接数 vs max_connections
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -tc "
  select count(*) as total, max_connections
  from pg_stat_activity, (select setting::int as max_connections from pg_settings where name='max_connections') t
  where datname is not null;"

# 各库连接分布
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select datname, count(*) total,
         count(*) filter (where state='idle') as idle,
         count(*) filter (where state='active') as active,
         count(*) filter (where state='idle in transaction') as idle_in_txn
  from pg_stat_activity where datname is not null
  group by datname order by total desc;"
```

**判定**：
- 连接数 **远低于 100**（如 < 50）但应用报超时 → **应用侧池打满**
- 连接数 **= 100 或接近** → **数据库侧打满**

### 第二步：定位占用来源

```bash
# 按用户/库/客户端 IP 分组，看谁占满连接
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select datname, usename, client_addr, state, count(*)
  from pg_stat_activity where datname is not null
  group by 1,2,3,4 order by 5 desc;"

# 排查长事务（idle in transaction，占着连接不释放，是打满的常见诱因）
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select pid, usename, datname, state,
         now()-xact_start as xact_age, left(query,80) as query
  from pg_stat_activity
  where xact_start is not null order by xact_start;"
```

**判定**：
- 连接集中在 `compassio` 用户、来自 backend Pod → 应用侧问题
- 大量 `idle in transaction` → **长事务不归还连接**，数据库侧堆积
- 大量纯 `idle` 且来源单一 → **连接泄漏/未关闭**，应用侧池管理问题

### 第三步：看应用侧日志确认

```bash
# 后端是否报连接池超时
kubectl logs deploy/compassio-backend -n compassio --tail=200 | grep -iE "TimeoutError|pool|overflow|could not connect|too many clients"

# 后端副本数（连接上限 = 副本数 × 15）
kubectl get deploy compassio-backend -n compassio -o jsonpath='{.spec.replicas}{"\n"}'
```

**判定**：
- 日志有 `TimeoutError / overflow` → 确认应用侧池打满
- 日志有 `could not connect / too many clients` → 确认数据库侧打满

## 五、结合本项目的判定与处理

### 场景 A：应用侧池打满

**特征**：PG 连接数不高（如 20–30），但后端报 `TimeoutError`、请求卡 30s 后 500。

**本项目根因**：
- 单 worker 池上限仅 **15**（默认 `pool_size=5 + max_overflow=10`），并发稍高即耗尽
- 连接归还慢（慢查询、长事务）或泄漏（未正确关闭 session）

**处理**：
```bash
# 温和：杀长事务/慢查询占用连接
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "select pg_cancel_backend(pid);"

# 根治：调大池参数 + 加 pool_pre_ping（见第六节加固）
# 临时扩容副本也能分摊连接压力
kubectl -n compassio scale deploy/compassio-backend --replicas=2
```

### 场景 B：数据库侧 max_connections 打满

**特征**：PG 连接数 = 100，应用报 `could not connect / too many clients`。

**本项目根因**：
- 共享集群，compassio + n8n + 运维连接共享 100 上限
- 多副本后端连接线性增长（每副本 15），副本越多越容易撞顶
- 长事务 / 连接泄漏导致连接堆积不释放

**处理**：
```bash
# 1. 定位并清理堆积连接（idle in transaction / 长 idle）
#    先用 pg_terminate_backend 清理异常连接，谨慎操作
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select pg_terminate_backend(pid)
  from pg_stat_activity
  where datname='compassio' and state='idle in transaction' and pid <> pg_backend_pid();"

# 2. 根治：上连接池中间件（PgBouncer），应用侧多副本共享少量 PG 连接
#    CNPG Pooler CR 或独立 PgBouncer，见第六节
```

## 六、加固建议

### 6.1 给引擎加池参数与探活（最直接）

在 `backend/app/db.py` 配置连接池，避免默认 15 的裸奔上限，并主动剔除坏连接：

```python
return create_async_engine(
    url,
    future=True,
    pool_size=10,          # 按需调整
    max_overflow=20,
    pool_pre_ping=True,    # 借出前探测，坏连接主动剔除
    pool_recycle=300,      # 定期回收，避免长连接失效
)
```

### 6.2 设置 application_name，让连接可溯源

当前 `application_name` 为空，定位时只能靠 Pod IP。给连接串加上应用标识，能直接从 `pg_stat_activity` 区分来源：

```
postgresql+asyncpg://compassio:***@pg16-ceph-rw.cnpg-system.svc:5432/compassio?application_name=compassio-backend
```

### 6.3 上连接池中间件（连接数治理的正解）

共享集群 + 多副本场景，应用直连 PG 会让连接数随副本线性增长，迟早撞 100。上 PgBouncer / CNPG Pooler，让多个应用连接复用少量 PG 连接，从根本上解决数据库侧打满：

```bash
# CNPG Pooler（推荐，与 CNPG 集成）
# 创建 Pooler CR，应用连 pooler 的 Service，而非直连 pg16-ceph-rw
```

### 6.4 连接数治理原则

- `max_connections=100` 是共享上限，不要为单个应用直接调大，先优化池 + 上中间件
- 多副本前先算连接账：`副本数 × 单worker池上限 ≤ 剩余连接预算`
- 监控 `pg_stat_activity`，重点看 `idle in transaction` 和连接总数趋势

## 七、一句话总结

> 连接池打满要分两层看：**应用侧池打满**（PG 连接数不高、报 `TimeoutError`，是池太小/归还慢/泄漏）与**数据库侧打满**（PG 连接数=100、报 `too many clients`，是连接总数超限）。定位先查 `pg_stat_activity` 连接数——远低于 100 是应用侧，接近 100 是数据库侧；再按来源/状态下钻。本项目无 PgBouncer、引擎未配池参数且 `application_name` 为空，定位靠 Pod IP，最该做的是加池参数、设 `application_name`、必要时上连接池中间件。
