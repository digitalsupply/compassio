# 慢查询定位与索引诊断分析

> 结合 Compassio 线上环境（CNPG `pg16-ceph`，PostgreSQL 16.13），分析如何定位到具体的慢 SQL 和索引问题。重点说明本项目当前定位工具链的实际约束，以及在约束下的可操作路径。

## 一、线上工具现状（定位前必须知道）

慢查询定位依赖几类工具，**本项目当前大部分未启用**，这决定了排查路径：

| 工具 | 状态 | 说明 |
| --- | --- | --- |
| `pg_stat_statements` | ❌ **未加载、未安装** | 历史 SQL 统计的最强工具，当前不可用；库内仅 `plpgsql` |
| `log_min_duration_statement` | ❌ **= -1（未开）** | 慢查询日志未开启，不会记录慢 SQL |
| `log_statement` | ❌ `none` | 不记录任何 SQL 日志 |
| `statement_timeout` | ❌ `0`（无超时） | 慢查询不会自动中断，可能长期占用 |
| `auto_explain` | ❌ 未开 | 不会自动记录执行计划 |
| `pg_stat_activity` | ✅ 可用 | 可抓**当前**正在执行的查询 |
| `EXPLAIN / EXPLAIN ANALYZE` | ✅ 可用 | 可对**指定** SQL 手动看计划 |
| `pg_stat_user_tables` / `pg_stat_user_indexes` | ⚠️ 可用但统计未刷新 | 需 `ANALYZE` 后才有准确数据 |
| OpenTelemetry 追踪 | ⚠️ 已集成（看配置） | 应用侧可看到慢请求及 SQL 耗时 |

**核心结论**：本项目**没有历史慢查询统计、没有慢查询日志**。定位慢查询当前只能靠**实时抓现行 + 应用侧追踪 + 手动 EXPLAIN**，要实现"回溯历史慢 SQL"必须先把工具启起来。

## 二、定位具体 SQL：四层方法

### 第一层：实时抓现行（当前最实用）

查询发生**当下**在跑的慢查询，抓正在执行的 SQL：

```bash
POD=$(kubectl -n cnpg-system get cluster pg16-ceph -o jsonpath='{.status.currentPrimary}')

# 当前所有活跃查询，按执行时长排序（query_age 最大的最慢）
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select pid, usename, datname, state,
         now()-query_start as query_age,
         left(query, 200) as query
  from pg_stat_activity
  where state='active' and datname is not null and pid <> pg_backend_pid()
  order by query_start;"

# 结合等待事件，判断是等锁还是等 IO/CPU
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c "
  select pid, wait_event_type, wait_event,
         now()-query_start as query_age, left(query,200) as query
  from pg_stat_activity
  where state='active' and wait_event_type is not null;"
```

- `query_age` 持续增大且 `wait_event_type='Lock'` → **等锁**，找阻塞源
- `wait_event_type` 为 `IO`/`CPU` → 慢在执行，需 EXPLAIN 看计划
- 抓到具体 SQL 后，进入第三层看执行计划

### 第二层：历史 SQL 统计（需启用 `pg_stat_statements`）

`pg_stat_statements` 记录所有 SQL 的执行次数与累计耗时，是**回溯历史慢 SQL 的核心工具**。本项目当前未装，启用后可按总耗时排序直接定位：

```sql
-- 启用后，按累计耗时找最慢的 SQL
select query, calls, total_exec_time, mean_exec_time, rows
from pg_stat_statements
order by total_exec_time desc
limit 20;
```

**启用步骤见第五节。** 启用前，历史慢 SQL 无法回溯，只能靠第一层实时抓。

### 第三层：慢查询日志（需启用 `log_min_duration_statement`）

开启后，PG 自动把所有慢于阈值的 SQL 记进日志，适合长期被动收集：

```yaml
# CNPG 参数（阈值 1 秒，按需调整）
log_min_duration_statement: "1s"
```

开启后从 Pod 日志查慢查询：

```bash
kubectl -n cnpg-system logs "$POD" -c postgres --tail=500 | grep -A 5 "duration:"
```

日志里会带执行时间、SQL 文本和**执行计划**（若同时开 `log_min_error_statement` 等）。

### 第四层：应用侧追踪（补充）

本项目集成了 OpenTelemetry，慢请求的链路里能看到 SQL 耗时。结合应用日志，能从"用户反馈慢"反查到具体接口和 SQL：

```bash
# 后端日志找慢请求
kubectl logs deploy/compassio-backend -n compassio --tail=200 | grep -iE "slow|duration|took"
```

## 三、定位索引问题：EXPLAIN + 表/索引统计

定位到具体 SQL 后，用执行计划和统计信息判断是否缺索引或索引失效。

### 3.1 EXPLAIN 看执行计划（最直接）

```sql
-- 只看计划，不执行
EXPLAIN SELECT * FROM public.users WHERE username = 'xxx';

-- 实际执行 + 缓存统计（真正跑一遍，写操作禁用）
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM public.users WHERE username = 'xxx';
```

**判断索引是否生效**：
- 看到 **`Seq Scan`（顺序扫描）** → 没走索引，大概率缺索引或索引失效
- 看到 **`Index Scan` / `Index Only Scan`** → 走索引了，但可能仍慢，看是否回表（`Heap Fetch`）、索引选择是否合理
- `EXPLAIN ANALYZE` 看 `actual time` 和 `rows`，判断实际耗时和扫描行数

> ⚠️ `EXPLAIN ANALYZE` 会真正执行 SQL，**写操作（INSERT/UPDATE/DELETE）禁用**，只对查询用。

### 3.2 表统计：顺序扫描次数找缺索引的表

`pg_stat_user_tables.seq_scan` 高，说明该表查询常未走索引。先刷新统计再查：

```sql
-- 先刷新统计信息（统计未刷新时结果不准/为空）
ANALYZE;

-- 顺序扫描次数高的表，可能缺索引
select relname, n_live_tup, seq_scan, idx_scan,
       pg_size_pretty(pg_total_relation_size(relid)) as size
from pg_stat_user_tables
where n_live_tup > 0
order by seq_scan desc
limit 15;
```

### 3.3 索引使用率：找无效/冗余索引

`idx_scan = 0` 的索引从未被用到，可能是冗余索引或建错列：

```sql
-- 从未被使用的索引（候选清理对象，但需结合 EXPLAIN 确认后再删）
select relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
from pg_stat_user_indexes
where idx_scan = 0
order by relname;

-- 索引大小，评估清理收益
select relname, indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) as size,
       idx_scan
from pg_stat_user_indexes
order by pg_relation_size(indexrelid) desc
limit 15;
```

> 删索引前务必用 `EXPLAIN` 验证：`idx_scan=0` 不代表无用，可能因统计未刷新或极少走到。用 `DROP INDEX CONCURRENTLY` 避免锁表。

## 四、本项目的实操路径

按**当前可用性**分两步：

### 当前（工具未启用）能做的

1. **实时抓**：`pg_stat_activity` 抓正在跑的慢查询（`query_age` + `wait_event_type`）
2. **应用侧**：otel 追踪 / 后端日志，从慢请求反查 SQL
3. **手动 EXPLAIN**：对抓到的 SQL 做 `EXPLAIN (ANALYZE, BUFFERS)` 看计划
4. **表/索引统计**：先 `ANALYZE` 刷新，再查 `pg_stat_user_tables` / `pg_stat_user_indexes`

### 启用工具后的完整能力

启用 `pg_stat_statements` + 慢查询日志后，可：
- 回溯历史最慢 SQL（`pg_stat_statements` 按 `total_exec_time` 排序）
- 被动收集慢 SQL 及执行计划（慢查询日志）
- 长期监控慢查询趋势

## 五、启用定位工具的步骤（CNPG）

`pg_stat_statements` 需要预加载到共享内存，要改 CNPG 参数并**重启**。共享集群影响 n8n，务必在维护窗口做。

> **关键坑**：`shared_preload_libraries` 是启动关键参数，**不能放进 `parameters`**——CNPG 会拒绝（`Can't set fixed configuration parameter`）。必须用专用字段 `spec.postgresql.shared_preload_libraries`（`[]string`，追加到默认值）。

```bash
# 1. 改 CNPG 参数
#    shared_preload_libraries 走专用字段，log_min_duration_statement 走 parameters
kubectl -n cnpg-system patch cluster pg16-ceph --type merge -p '{
  "spec":{"postgresql":{
    "shared_preload_libraries":["pg_stat_statements"],
    "parameters":{"log_min_duration_statement":"1s"}
  }}}'

# 2. 重启实例使 shared_preload_libraries 生效（log_min_duration_statement 运行时即生效）
#    无 cnpg 插件时用原生滚动重启：
#    先删备库 Pod（安全，主库不受影响），等待就绪；
#    再删主库 Pod（触发 CNPG 自动 failover，已加载新参数的备库升主，原主库重建为备库）
#    共享集群，先和 n8n 业务确认维护窗口
kubectl -n cnpg-system delete pod <备库Pod名> --wait=false   # 等待 ready 后继续
kubectl -n cnpg-system delete pod <主库Pod名> --wait=false   # 等待集群恢复 healthy

# 3. 在目标库创建扩展（每个用到的库都要建）
POD=$(kubectl -n cnpg-system get cluster pg16-ceph -o jsonpath='{.status.currentPrimary}')
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -d compassio -c \
  "create extension if not exists pg_stat_statements;"

# 4. 验证
# 参数生效
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -c \
  "show shared_preload_libraries; show log_min_duration_statement;"
# pg_stat_statements 统计（执行若干查询后）
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -d compassio -c \
  "select query, calls, round(total_exec_time::numeric,2) as total_ms
   from pg_stat_statements order by total_exec_time desc limit 10;"
# 慢查询日志（执行 pg_sleep(2) 后查容器日志，应见 duration: 记录）
kubectl -n cnpg-system exec "$POD" -c postgres -- psql -U postgres -d compassio -c "select pg_sleep(2);"
kubectl -n cnpg-system logs "$POD" -c postgres --tail=100 | grep "duration:"
```

> 参数改完部分需重启，`primaryUpdateStrategy=unsupervised` 时 Operator 可能自动重启主库，务必在维护窗口操作。

## 六、端到端排查流程

1. **发现慢**：用户反馈慢 / 监控告警 / 应用日志慢请求
2. **实时抓**：`pg_stat_activity` 抓当前 `query_age` 大的 SQL
3. **看计划**：对该 SQL 做 `EXPLAIN (ANALYZE, BUFFERS)`，看是否 `Seq Scan`、扫描行数、回表
4. **查统计**：`ANALYZE` 后看 `pg_stat_user_tables.seq_scan`、`pg_stat_user_indexes.idx_scan`
5. **判断索引**：缺索引 → 建索引（大表用 `CREATE INDEX CONCURRENTLY`）；索引失效 → 检查列/统计；冗余索引 → 评估后 `DROP INDEX CONCURRENTLY`
6. **回溯历史**（工具启用后）：`pg_stat_statements` 按 `total_exec_time` 找最慢 SQL，持续优化
7. **验证**：重新 `EXPLAIN` 确认走索引，观察 `query_age` / 慢查询日志是否消失

## 七、一句话总结

> Compassio 当前**没有 `pg_stat_statements`、没有慢查询日志**，定位慢 SQL 只能靠**实时抓 `pg_stat_activity` + 应用侧追踪 + 手动 `EXPLAIN`**；定位索引靠 `EXPLAIN` 看是否 `Seq Scan`，辅以 `pg_stat_user_tables.seq_scan` 和 `pg_stat_user_indexes.idx_scan`。要实现历史慢 SQL 回溯，需在 CNPG 开启 `shared_preload_libraries=pg_stat_statements` 和 `log_min_duration_statement`，注意共享集群重启影响 n8n。
