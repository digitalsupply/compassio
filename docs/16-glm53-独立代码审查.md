## 1. 项目定位（README/SPEC 摘要）

Compassio 是一个由大模型驱动的**校级心理健康测评系统**（学生 MHT/MSSMHS + 教师 self-care 量表），核心契约在 SPEC.md 中被明确固化为"已定事实"：

- **计分是纯确定性引擎，LLM 绝不参与计分**（只做出题重排与结论措辞，且失败必须回退）。
- **教师测评数据对 school_admin 硬性不可见**，任何接口/导出/统计不得泄漏。
- **LLM 成本可控**：默认 `fusion` 策略，规则每题选题，LLM 每 12~20 题随机检查点才参与一次（100 题 MHT 约调 5~8 次而非 84 次），支持 `rules_only` 完全关闭。
- 双部署形态（docker-compose + K8s kustomize），题目库 JSON 热替换、不改代码。

SPEC 是一份罕见的"施工图式"规格书：权限矩阵、API 清单、算法（CAT-lite 两阶段）、回退语义、测试验收标准（DoD）都被明确定义，代码实现与 SPEC 逐条对应（fusion/checkpoint/预取/risk 规则驱动/教师隐私豁免均能找到实现与测试）。这是本项目工程质量的重要加分项。

## 2. 后端架构分析（backend/app，后端共 ~5900 行源码）

### 2.1 模块划分总览

```
backend/app/
├── main.py (519)        # FastAPI 入口：lifespan、路由注册、健康检查/依赖探活、HTTP 观测中间件
├── config.py (82)       # Pydantic Settings（env 驱动，别名规范）
├── db.py (90)           # engine/sessionmaker/Redis 客户端，JSONB/JSON variant 兼容 sqlite
├── models.py (207)      # SQLAlchemy 2.0 Mapped 风格 ORM，9 张表
├── schemas.py (326)     # Pydantic v2 DTO
├── security.py (80)     # JWT + bcrypt + require_role 依赖
├── next_cache.py (205)  # "下一题"预取缓存（Redis 优先 + 进程内 LRU 兜底）
├── export_service.py(241)# 班级结果导出（xlsx/csv），管理员与班主任共用
├── routers/             # 10 个路由模块（auth/import/users/assess/notify/report/teacher/llm/scales/admin）
├── engine/              # 领域核心：scoring / adaptive / checkpoint / risk / conclusion
├── llm/                 # provider（OpenAI 兼容抽象）/ presets（8 家）/ service（DB 配置解析）
├── observability/       # metrics（Prometheus）/ tracing（OTel，可安全降级为 no-op）/ logging（JSON 结构化）
└── scales/data/*.json   # 三套量表题库（禁改）
```

分层是教科书式的：**routers（传输层）→ engine（领域层，纯函数为主）→ llm（外部依赖抽象）→ observability（横切面）**。

### 2.2 engine/ —— 领域核心，质量最高

- **scoring.py（181 行，纯函数）**：三个量表计分完全按 JSON 规则驱动，无任何 I/O、无 LLM。MHT 效度作废（≥7 作废）、三级分级、MSSMHS 因子均分、teacher_ref reverse 题 `7-raw` 反转全部实现正确并有边界测试覆盖。
- **adaptive.py（353 行）**：`pick_next_item` 返回 `(item_id, transition, fallback_used, source)`，source 明确区分 `rule_coverage / rule_weighted / llm_fusion / llm / rule_fallback / finished`，便于指标归因。LLM 输出校验严格（候选集过滤、去重、兼容 legacy `item_id` 形态），检查点 8s 硬超时异常即回退规则选题——SPEC §6.2 的约束逐条落地。
- **checkpoint.py（142 行）**：检查点调度状态以 `random.Random(f"{assessment_id}:{count}")` 播种，**同一测评可复现且不污染全局 RNG**；Redis 不可用时进程内 LRU 兜底；幂等（重发 /next 不会双消费检查点）。
- **risk.py（78 行）**：通用规则引擎（7 种条件算子），`should_notify_admin` 从入口处硬编码 `teacher_ref 永不通知`——隐私红线在引擎层就有保护。

### 2.3 llm/ —— 抽象干净、细节讲究

- `provider.py`：单一开尔文抽象（`chat/ping/reachable`），`extra_headers` 支持 `{{uuid}}` 模板展开（opencode-go 的 `x-opencode-session` 每请求随机）；截断自动放大 `max_tokens` 重试一次（针对推理模型思考吃 token 的实测问题）。
- `reachable()` 是亮点：发送**故意不完整的请求**（只有 model 无 messages）用 400/401 区分"凭据有效但请求非法"与"凭据无效"，实现**零 token 消耗**的探活——这是省成本的聪明设计。
- `service.resolve_provider`：DB 配置优先、env 预设回退，干净且无副作用。

### 2.4 observability/ —— 超出常规交付水准

- **metrics.py**：全部低基数设计——HTTP 指标用**路由模板**（`/api/assess/{id}/next`）而非具体路径，杜绝标签爆炸；还把"缓存未命中"细分为 `no_prefetch`（规则兜底，正常）与 `llm_blocked`（真的在等 LLM），把"命中率"纠偏成"学生真实等待"，`next_llm_wait_seconds` 只统计前台同步等待、预取后台不计——指标语义考究。
- **tracing.py**：OTel 未装/未配置时全部 no-op，`start_span`/`set_span_attributes` 任何异常均吞掉，**观测永不成为可用性依赖**（文档与代码一致）。
- **logging.py**：JSON 结构化日志，自动注入 trace_id/span_id（Loki↔Tempo 互查），显式注释"不得记录密码/手机号/题干原文"。
- **main.py 的依赖探活**：LLM 健康状态放 Redis 跨 worker 共享（uvicorn 2 worker 不各探各的）、免额度探活 + 付费 ping 双层节流、失败缩短重试间隔、`SET NX` 名额串行化并发探活——生产实测踩坑后打磨的痕迹明显。

### 2.5 routers/ —— 职责清晰但个别模块过胖

- `assess.py`（526 行）承载了测评全流程：start/next/answer/finish/my-results/report。权限判定（`_load_assessment` 归属校验 + `_can_access_scale` 学段×受众双重判定）、断点续答复用、upsert 应答、每次 answer 后同步 risk 评估与预取调度均在其中。
- `teacher.py` 头部 docstring 直接写明硬约束："教师结果对 school_admin 永远不可见；越权访问其他班级一律 403"，且用 `_ensure_own_class` 强制校验 class_id 参数。
- `import_.py` 处理了大量脏数据现实（全角括号、初一→七年级别名、同名教师按班匹配、行级错误全量收集不半途失败）。
- `users.py`/`import_.py` 之间存在轻微的循环复用（users 复用 import_ 的 `_infer_grade_level` 等私有函数）。

### 2.6 横向设计能力

三处体现**优雅降级**的一致策略：预取缓存、检查点调度、LLM 探活均为"Redis 优先 + 进程内兜底 + 失败永不外泄"（`next_cache.prefetch_next` 吞掉所有异常且保留 `CancelledError` 传播的正确姿势；预取任务以强引用集合防 GC）。这种对故障模式的系统性思考是本项目区别于"一次性交付"代码的关键。

## 3. 前端结构分析（frontend/src，~2200 行）


质量评价：

## 4. 代码质量专项评价

### 4.1 分层 —— 优秀（9/10）

- routers 不做业务计算：计分/预警/结论全部下沉 engine，且 engine 内部是可独立单测的纯函数/无状态模块。
- concerns 分离讲究：预取调度（next_cache）、检查点调度（checkpoint）、导出（export_service）从路由中独立成服务模块。
- 扣分点：`main.py` 承担过多（见缺点 1）；`assess.py` 中 `_maybe_create_notification`（含通知去重）属领域逻辑，更适合放 service 层。

### 4.2 类型标注 —— 良好（8/10）

- ORM 全面采用 SQLAlchemy 2.0 `Mapped[...]`/`mapped_column` 类型化写法；函数签名普遍标注（`str | None`、`tuple[bool, str]`、`Callable[[dict], Awaitable[...]]` 等 Py3.10+ 语法）；schemas 全 Pydantic v2（`model_config = ConfigDict(from_attributes=True)`）。
- 扣分点：量表 payload 是 `dict` 无 TypedDict/Pydantic Schema 约束（`scale["items"]` 等字典访问式编程，schema 变更只能靠测试兜底）；部分内部函数返回 loose dict（如 `pick_next_item` 的 `scale: dict`）。前端 TypeScript 类型完好但个别 `as any`（stores/auth.ts 的 localStorage 读取）。

### 4.3 错误处理 —— 良好（8.5/10）

- LLM 全链路"失败即回退"：超时 8s→规则选题；结论失败→确定性模板；`fallback_used` 持久化到 results 并计入指标，可审计。
- 输入校验完整：answer 校验题号/选项值合法性、finish 校验未答完题数、400 错误信息中文化且具体。
- observability 三件套（metrics/tracing/logging）全部 best-effort，任何观测故障不影响主链路。
- 扣分点：`_maybe_create_notification` 有一次**已执行但结果被丢弃的查询**（传入查询结果未使用，紧接重复查询——明显的代码瑕疵）；通知去重按 title+body 文本匹配，并发下有重复通知风险；多数路由依赖 session close 隐式回滚，commit 失败路径无显式 try/rollback。

### 4.4 测试覆盖 —— 良好（8/10）

- 15 个测试文件 / 97 个用例，全部真实通过（实测 72s）。覆盖矩阵对齐 SPEC §11：计分三量表边界（≤55/56/≥65、效度 6/7 分界、reverse 反转）、risk 规则、权限隔离（学生访问教师量表 403、班主任越权班级 403）、adaptive LLM 失败回退与候选集约束、导入、打印名单、导出、next_cache、observability。
- conftest 设计合理：env 先行（在 app import 前固定 sqlite/关闭 LLM/tracing）、依赖注入覆盖 `get_db`、session 级 settings 缓存清理。
- 扣分点：无覆盖率门禁（未跑 `--cov`，无法断言分支覆盖）；结论生成（conclusion.py）与 provider 的 HTTP 语义测试较薄（test_llm_probe 有覆盖但 mock 手写较多）；main.py 的依赖探活/共享健康逻辑仅部分可达；**前端无任何测试**。

### 4.5 安全 —— 中上（7/10）

- RBAC 抽象正确（`require_role` 闭包 + FastAPI Depends），教师隐私在三个层面强制（路由层 ownership 过滤、admin 侧无端点、docstring 红线声明）。
- 扣分点（按严重度）：
  1. `initial_password` **明文入库**（业务上为打印下发所需，是有意决策且有"本人改密后清空"的缓解，但仍是攻击面：DB 泄漏 = 全校账号明文密码）；
  2. `_gen_password` 用 **`random` 模块而非 `secrets`**（可预测，安全敏感场景应换 `secrets.choice`）；
  3. `SECRET_KEY` 默认值 `"change-me-in-production"` 无启动强校验；
  4. JWT 无刷新/撤销机制（24h 有效期 + 修改密码后旧 token 仍有效）。

## 5. 优点列表

1. **SPEC 驱动且实现高度对齐**：权限矩阵/算法/回退语义/验收标准逐条可追溯、有测试背书。
2. **领域核心纯净**：scoring/risk 是纯函数、JSON 规则驱动、零 LLM 零 I/O——"LLM 不参与计分"的红线由架构保证而非纪律保证。
3. **成本与体验工程极强**：fusion 检查点策略（~84 次→5-8 次 LLM 调用）+ 答后预取（学生 <20ms 拿下一题）+ `reachable()` 零 token 探活 + `next_llm_wait_seconds` 只统计真实等待。
4. **可观测性达到生产级**：低基数路由模板指标、结构化日志注入 trace_id、OTel 可安全降级、依赖探活结果跨 worker 经 Redis 共享。
5. **一致的优雅降级策略**：Redis 优先 + 进程内 LRU 兜底出现在缓存/调度/探活三处，故障模式经过系统性思考。
6. **类型化程度高于同类业务代码**：SQLAlchemy 2.0 Typed ORM + Pydantic v2 + 现代联合类型语法 + 前端完整 DTO 类型。
7. **97 个测试全绿且语义精准**（边界值、权限隔离、回退、幂等）。
8. **中文注释/文档质量高**：大量"为什么"注释记录实测踩坑（如 worker 各说各话、推理模型 ping 产生两次上游调用），新人可快速建立上下文。
9. **现实数据容错充分**：班级名规范化、同名教师按班区分、行级错误全量收集。

## 6. 缺点列表

1. **main.py 过载（519 行）**：健康探活状态机、路由模板索引、种子装载、轻量迁移、观测中间件混在入口文件，应拆出 `health.py`/`middleware.py`。
2. **明显代码瑕疵**：`assess._maybe_create_notification` 第一次 `db.execute(select(Notification)...)` 的结果被丢弃后重复查询；文本匹配去重在并发下不可靠。
3. **密码系统薄弱**：`random` 而非 `secrets` 生成初始密码；初始密码明文入库；`SECRET_KEY` 默认值无启动检查；改密不吊销旧 JWT。
4. **schema 无类型化**：量表 payload 以裸 dict 贯穿 engine/adaptive/scoring，Pydantic 模型缺失，重构依赖测试兜底。
5. **无 Alembic**：以 `create_all` + 手写 `ALTER TABLE IF NOT EXISTS` 轻量迁移代替（自评"轻量"，但多 worker 并发首次建表与未来索引变更会失控）。
6. **前端零测试、零 lint 工具链**：类型门禁之外无任何质量护栏。
7. **通知写入无审计**：`audit_logs` 表建了但使用稀疏（多数敏感操作如批量重置密码时有写，其他管理操作覆盖不全）。
8. **测试缺乏覆盖率度量**：无法量化分支覆盖，conclusion/探活等分支丰富的模块覆盖偏薄。
9. 横向小问题：users.py 直接 import 兄弟模块的私有函数（`from app.routers.import_ import _infer_grade_level`）；routers 未统一导出路由树（`include_router` 前缀分散在 main.py）。
