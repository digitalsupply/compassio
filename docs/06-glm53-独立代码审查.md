## 一、项目定位（README + SPEC 交叉确认）

Compassio 是一个**校级心理健康测评系统**，核心契约可归纳为：

| 维度 | 定位 |
|---|---|
| 业务形态 | 三套量表（MHT 100 题 / MSSMHS 60 题 / 教师参考量表 60 题）在线作答 → 确定性计分 → LLM 措辞结论 → 分角色查看 |
| 角色模型 | `school_admin` / `teacher` / `student` 三角色 RBAC |
| LLM 边界（项目安全底线） | **只准选题与措辞，绝不参与计分**；成本用 fusion 策略压制（100 题 MHT 约 5~8 次调用而非 84 次） |
| 隐私硬规则 | 教师测评结果对任何 admin **结构性不可见**；教师预警永不写通知表 |
| 技术底座 | Vue3+TS+Element Plus+ECharts / FastAPI(async)+SQLAlchemy 2.0 async / PG+Redis；compose 与 K8s(GitOps) 双部署 |
| 并发目标 | 单校 ≤3000 账号、峰值 300 人同时作答 |

SPEC.md 作为"唯一施工图"，在实现中逐条可找到对应物（策略开关、检查点间隔、脱敏 prompt、隐私矩阵），**文档与代码一致性在同类项目中属于罕见的高水准**。

## 二、后端架构分析（`backend/app`）

### 2.1 模块划分总览（5,466 行 Python）

```
app/
├── main.py (519)      # 入口：lifespan、建表+轻量迁移、健康检查、探活调度、HTTP 中间件
├── config.py (82)     # Pydantic Settings，env 全覆盖，注释索引到 SPEC 条款
├── db.py (90)         # 懒初始化 engine/session/redis；JSONB variant（PG→JSONB，其余→JSON）
├── models.py (207)    # SQLAlchemy 2.0 Mapped 风格，8 张表 + 枚举
├── schemas.py (326)   # Pydantic v2 DTO
├── security.py (80)   # JWT/bcrypt + require_role 依赖注入工厂
├── next_cache.py (205)# next-item 预取缓存（Redis 主 + 进程内 LRU 兜底）
├── export_service.py  # 班级结果 xlsx/csv 导出
├── routers/ (11 个)   # auth/import/users/assess/notify/report/teacher/llm/scales/admin
├── engine/            # scoring(181) 纯函数计分 / adaptive(353) 融合出题 / risk(78) 规则预警
│                      # conclusion(150) 结论+模板回退 / checkpoint(142) LLM 检查点调度
└── llm/               # provider(185) OpenAI 兼容抽象 / service(46) DB优先解析 / presets(51)
```

### 2.2 值得肯定的架构决策

1. **"LLM 永不阻塞可用性"贯穿全链路**（这是本项目最出色的设计主线）：
   - `engine/adaptive.py`：检查点 LLM 调用包了 8s 硬超时，超时/异常/非法 JSON 三级全走 `rule_fallback`，并以 `source` 枚举（`rule_coverage/rule_weighted/llm_fusion/rule_fallback/finished`）显式标注每个选题的来源，可观测、可回放；
   - `engine/conclusion.py`：LLM 失败无缝切换 `_template_conclusion`（确定性文案按 level + 高风险维度名拼接），`fallback_used` 落库；
   - `llm/provider.py`：400/截断重试、推理模型空 content 自动放大 max_tokens（带理由注释），`ping()` 与 `reachable()` 刻意分离——`reachable()` 发"故意不完整请求"来**免额度探测凭据**（400=凭据有效，401=凭据无效），是非常聪明的网关探测设计；
   - `main.py`：LLM 健康值经 **Redis 跨共享 + SET NX 锁** 在 2 worker × 2 pod 集群全局节流，收尾还留了进程内兜底——对分布式探活去重的理解到位；
   - `next_cache.py`：预取任务 fire-and-forget、强引用防 GC、Redis 失败静默降级 LRU(500)——学生侧永不付 LLM 等待。

2. **隐私硬规则做了多重冗余防护**：`teacher.py` 量表白名单 `_CLASS_SCALES=("mht","mssmhs")` + `should_notify_admin` 对 `teacher_ref` 恒 False + `assess.py` admin 只能看学生测评为 target + ORM 层 `user_id` 强制过滤，且测试文件 `test_permissions.py` 专门断言，不做单点防御。

3. **计分引擎是教科书式的纯函数**：`engine/scoring.py` 只依赖 `(scale dict, answers dict)`，无 IO、无状态、LLM 零参与，可独立单测，边界值（效度作废、reverse 反转、bands）全部落在测试里。

4. **可观测性达到生产 SRE 水准**：
   - HTTP 指标用**路由模板**（正则索引缓存）而非具体路径，杜绝基数爆炸；
   - `compassio_next_llm_wait_seconds` 只统计前台 `/next` 真实等待、预取不计数——把"命中率"纠偏成"学生是否真的在等"，这是业务语义级的指标设计；
   - tracing 全部 no-op safe，" Observability must never be an availability dependency" 在 metrics/tracing/logging 三个文件中被 `except Exception` 一致执行。

### 2.3 架构短板

1. **没有 service 层，业务逻辑直接堆在 router 里**：`assess.py`（526 行）、`users.py`（437 行）、`import_.py`（412 行）承担了 DTO 组装、biz 逻辑、查询拼装的复合职责；`users.py`/`import_.py` 里手写拼音转用户名、班级规范化、生成初始密码等可复用逻辑无法脱离 HTTP 上下文调用，测试也得开 ASGI client 才够到。
2. **没有 schema 校验层护住"量表 JSON"**：`scale.dict` 全库以 `dict[str, Any]` 流转，`mht/mssmhs/teacher_ref.json` 三个文件是全局数据契约但落库后靠运行时 Key 访问，admin 后台上传热替换 JSON 却没有前后 schema 断言，字段拼错（如 `high_cutoff`/`invalid_cutoff`）会静默走默认值，属于一处真实风险。
3. **main.py 是 519 行杂烩**：lifespan / 建表 + 手写 `_apply_light_migrations` / LLM 双层探活 / 健康端点 / 中间件 / `/metrics` 全在一个文件，且 `_iter_route_templates` 依赖 FastAPI 内部属性（`original_router`、`include_context`），升级 FastAPI 后有脆弱性。
4. **Alembic 缺位**：`requirements.txt` 列了 `alembic>=1.13`，但仓库没有 alembic 目录；现实中用启动时 `ADD COLUMN IF NOT EXISTS` 顶替——列内型变更/索引/数据迁移将无解。
5. `models.py` 中 `User.assessments` 全局 `lazy="selectin"`，任何时候查询 User 都会级联抓取全部 assessments——这个规模下可接受，但属于隐式过度抓取。

## 三、前端结构分析（`frontend/src`，约 4,831 行）

```
src/
├── api/        client.ts（axios 实例+拦截器） + services.ts（按域分组的强类型泛型封装 + 下载工具）
├── types/      index.ts（250 行接口定义，与后端 DTO 一一对应）
├── stores/     auth.ts（setup 风格，含脏会话自愈） / notify.ts
├── router/     index.ts（角色 meta + 守卫五段式注释）
├── components/ AssessRun.vue / ReportCard.vue（ECharts 雷达） / CriticalBanner.vue / 品牌组件
└── views/      admin×6 / student×3 / teacher×3 + Login/Home/ChangePassword
```

亮点：
- **api 层纪律好**：所有端点集中、请求/响应均有 TS interface，视图里不直接出现裸 `axios` URL；文件下载（content-disposition 兼容 RFC5987 编码）单独成 utils 并有 try/catch 解码兜底。
- **路由守卫认真处理了脏回路**：`hasValidSession = token && role∈KNOWN_ROLES`，先清理脏 localStorage 再判定，避免"首页↔守卫"死循环（SPEC §9 列出的行为与代码一致）。
- 视图分域清晰，单文件组件 60~518 行，无巨型页面。

短板：
- **零测试**：无 vitest/jest，无 E2E（Playwright/Cypress）——登录、作答流、角色分流全是手工冒烟；
- 类型严格度打折：`finish` 返回 `any`、`answer` 的 `risk_flags: any[]`、store 内个别 `as any`（总体 ≤3 处，克制但存在）；
- `stores/auth.ts` 角色存 localStorage 前后端**以"信任客户端"为前提**（后端每次鉴权查库所以不构成安全洞，只是 UX 层假象风险）。

## 四、代码质量评价

### 4.1 分层与职责 —— 4/5
见 2.2/2.3。routers→engine/llm 的依赖方向干净（engine 不 import routers），`security.require_role` 工厂统一了角色断言，engine 层完全可独立测试；扣分在 service 层缺位导致 router 增重。

### 4.2 类型标注 —— 3.5/5
- Python 风格新派（`Mapped[]`、`Annotated`、`str | None`、说清注释），函数签名标注率高；
- 但核心领域数据（量表 JSON、scores dict）皆 `dict[str, Any]`，`TypedDict` / pydantic 模型拆一步没有做；
- **无 mypy/pyright 配置、无 pre-commit**，类型纯靠 FastAPI/pydantic 运行时与 vue-tsc（前端 build 时跑 `vue-tsc --noEmit`）兜底。

### 4.3 错误处理 —— 3.5/5
- 好的一面：LLM 全链路**显式分级回退**而非"崩了就崩"；HTTP 统一中文 `HTTPException` detail；下游降级路径（Redis 挂了→内存 LRU、tracing 缺依赖→no-op）全部真实实现；
- 值得指出的具体瑕疵：
  - `except Exception` 全库约 **34 处且多数静默 pass**（很多标注了 `# pragma: no cover - defensive`，但吞掉真实 bug 的代价仍然存在，尤其 `db_redis`、`metrics`）；
  - `assess.py::_maybe_create_notification` 里有一段**查询结果被丢弃的废代码**（同一 select 连续执行两次，第一次完全没使用），且 TOCTOU 竞态——两个 worker 并发命中 critical 时可能重复记录同一个预警；
  - `submit_answer` 的 upsert 是"先查再插"，并发重放同一 (assessment_id, item_id) 将撞唯一约束（有约束兜底不脏数据，但会 500）；
  - `config.py` `secret_key` 默认 `"change-me-in-production"`，启动时不校验，生产不配 env 会**静默接受默认密钥**；
   - `initial_password`（初始密码明文入库供打印，SPEC 已声明这是业务权衡，但审计视角下仍是攻击面的最长尾）。

### 4.4 测试覆盖 —— 4/5
实测 `pytest -q` → **97 passed**。覆盖面与 SPEC §11 的验收要求严格对齐：
- `test_scoring`（三量表 + 效度作废 + reverse 反转 + bands 边界）、`test_risk`（MHT 85 / MSSMHS 30 / teacher 不通知）、`test_permissions`（学生访问 teacher_ref→403、admin 无教师结果端点的路由级断言）——这些正是关键 hard-rule 的回归锁；
- 覆盖了 adaptive 回退/候选约束/预取缓存/导入/导出/账号管理/可观测性探活（test_llm_probe 394 行，罕见地对"探活分级"做了测试）；
- 缺口：无 coverage 工具量化、PG-only 行为（JSONB/复制）未在测试中体现、前端 **0 测试**。

### 4.5 可维护性与文档 —— 5/5
注释密度与质量极高——大量"why"型注释（如 `ping()` 为什么不复用 `chat()`、bcrypt 版本 pin 的兼容性原因、指标口径纠偏理由），且中文注释自然服务于团队。repo 内 15 份 docs/ 编号交付文档 + SPEC 的"已定事实"清单共同形成可追溯的决策链。

## 五、优点列表

1. **契约先行**：SPEC.md 作为单一事实源，行为契约（策略开关/阈值/隐私矩阵/prompt 原则）在代码中逐条对应，文档↔代码漂移极小。
2. **"LLM 不阻塞可用性"做到了军规级别**：超时/回退/降级/模板结论/预取缓存/降级加权，整条链路在极端故障下面向学生仍然完整可用。
3. **成本工程意识**：融合策略把 LLM 调用从 84 次/百题压到 5~8 次；`rules_only` 一键零成本；探活区分免额度/付费两级。
4. **隐私与安全的多重防线**：RBAC 依赖注入 + 量表白名单 + ORM 层过滤 + 教师预警永不入通知表 + 测试断言锁死——单点失效不致泄漏。
5. **可观测性生产级**：低基数路由模板指标、业务语义指标（学生真实等待）、全链路 tracing no-op safe、健康探针三态分离（live/readiness）。
6. **降级一以贯之**：Redis 不可用→进程内 LRU 与跨进程节流兜底、tracing/otel 缺依赖不致命、metrics 永不抛错。
7. **计分纯函数化** + 测试边界全覆盖，核心数字可信。
8. **注释与文档质量**在同类交付项目中显著高于平均水平，且回答了"为什么"而不只是"是什么"。
9. **测试真实可跑**：97 用例不依赖外部服务，conftest 用 sqlite 内存 + ASGI transport，新人克隆即测。
10. 依赖克制（SPEC 禁止 LangChain/Celery），技术选型与规模匹配，Dockerfile/compose/k8s 双形态齐备。

## 六、缺点列表

1. **router 臃肿、无 service 层**：assess/users/import 合计 1,375 行承载业务逻辑，核心业务函数不可脱离 FastAPI 上下文复用。
2. **量表 JSON 无 schema 校验**：管理员热替换题目库后只按"运行时 KeyError"暴露问题，`Any` 流转全库。
3. **类型体系缺口**：无 mypy/pyright 配置；关键前置标量（scale/answered）精度低；前端个别 `any`。
4. **防御式编程过度**：约 34 处 `except Exception`（多数静默）吞掉了本应可观测的中间失败，排障主要依赖日志与 span。
5. **并发细节瑕疵**：预警去重 TOCTOU、作答 upsert 非原子（唯一约束兜底但用户体验是 500）、以及 `_maybe_create_notification` 中明显的废弃查询（代码异味 + 一次多余 DB 往返）。
6. **迁移方案弱**：alembic 仅存在于依赖清单，实际是启动时 `ADD COLUMN IF NOT EXISTS`，无法演进 schema。
7. **`secret_key` 默认值无启动校验**，生产错配会静默运行。
8. **前端零测试**：核心交互（作答流/断点续答/权限分流）无任何自动化。
9. **初始密码明文入库**（业务权衡，但该列构成的敏感数据面最大，需 DB 级管控配合）。
10. `main.py` 杂烩 + 依赖 FastAPI 内部属性做路由模板解析，升级脆弱性隐患。

> 综合判断：这是一份**以"韧性工程 + 文档契约"见长的高质量交付型代码**。它最闪光的地方不是功能，而是对故障的系统性预演（LLM 超时、Redis 失联、推理模型空输出、探活额度），以及 privacy 硬规则的落地方式。主要欠账集中在两类工程卫生问题：**类型/静态工具链缺位**与**业务逻辑层（service 层与 schema 校验）的抽离**。若补上这两项 + 前端最低限度的 E2E，可稳固进入 9 分档。

### 优先改进建议（按 ROI 排序）

1. **给量表 JSON 加 pydantic（或 TypedDict+断言）校验**，在 `_seed_scales` 与 admin reload 端点上做 fail-fast 校验 —— 一天内可完成，收益最大；
2. 从 `assess.py`/`users.py` 抽出 `services/`（计分编排、通知、账号工厂），router 只留 request/response；
3. 修复 `_maybe_create_notification` 的废查询，并用 `INSERT ... ON CONFLICT DO NOTHING` 或基于 assessment_id 的去重键消除预警 TOCTOU；
4. `answer` upsert 改为原子 upsert（PG `INSERT ... ON CONFLICT (assessment_id, item_id) DO UPDATE`）；
5. secret_key/DB 密码等生产必配项在启动时强校验（缺省即退出）；
6. 引入 mypy（宽松起步）+ coverage 下限 60% 起，前端补一条 Playwright 主链路冒烟（登录→作答→报告）；
7. 把 `alembic` 真正落地（或从 requirements 移除），替代 `_apply_light_migrations`。
